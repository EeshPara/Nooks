# Narrow discarded-publication retention proposal

Proposal only: no backend changes made. Applies to the reproducible 100-discarded-intent capacity issue in `creator-backend-audit-2026-10-08.md`. Keep pending custom-art differences between app/web/cloud intact.

A minimal fix can expire **only discarded, never-committed** publication intents after a defined 12-hour recovery window. Deleting a draft currently marks only `prepared` intents as `discarded`; publication in `publishing` or `retry-needed` blocks deletion. That CAS ordering makes discarded state distinct from an ambiguous or completed community write.

1. When draft deletion first marks a prepared intent discarded, set `discardedAt` and `expiresAt = discardedAt + 12h` in the same workspace transaction. Never extend this on retries.
2. Before creator writes, prune discarded records whose valid expiry has passed. For legacy discarded records without timestamps, set their first observed discard/expiry timestamps during the successful transaction and retain them for the full window; do not infer an old deletion date from creation time. Malformed/future timestamps must not make records eligible prematurely.
3. Never prune `prepared`, `publishing`, `retry-needed`, `published` or `failed` records in this change. In particular published and ambiguous commits retain their durable idempotency identity. Old committed requests must still recover the same community indefinitely under the current contract.
4. Keep the existing 100-record ceiling. If recently discarded records fill it, return precise retry guidance/earliest expiry rather than “remove old drafts.” If the retained non-expiring history fills it, say that the publication history limit is reached; do not promise deletion will clear it. Address compact published receipt storage separately if the product needs more than the current bounded history.
5. After expiry, the removed old **intent ID** must always be NOT_FOUND on commit. A new prepared review receives a fresh server intent UUID. Reusing a client request key for a recreated draft after the discarded window creates a new explicitly reviewed request, never resurrects the old intent or silently publishes. Document this narrow failed/discarded retry window; successful publication idempotency is unchanged.

The existing server stores intents only in the owner's workspace and commits via revision CAS. Implement pruning there, with no schema migration, background job, provider change or live content sweep. Reads may report expiry but should not trigger cleanup writes. Do not remove unrelated creator records, artwork receipts or Storage references.

Required local regressions: 100 discarded entries reject before expiry and allow a new prepare at/after the boundary; first discard timestamp stays stable; legacy entries get a full window; invalid dates remain retained; repeated published commit still returns the original community; retry-needed/publishing are never pruned; stale old intent cannot commit after expiry; concurrent delete/commit/CAS retry never expires an in-flight write; failed transaction never persists pruning. Include an honest cap message for 100 protected published receipts. Root/grader should review the 12-hour policy before implementation. No additional hosted run is necessary solely to exercise time-based pruning; use an injected clock and real creator/store transaction contracts.

## Independent review caveat

The grader identified a legacy initialization edge: if a prepare transaction stamps legacy discarded entries and then fails the 100-record limit, those timestamps roll back. Repeating prepare cannot start the expiry clock. Before implementation, choose an explicit successful creator-write initialization path (such as saving a draft edit), and give accurate guidance to perform that action; do not secretly persist partial changes from a failed prepare. Add a regression with 100 legacy discarded entries plus an existing valid draft. Validate expiry is exactly discard time plus the chosen TTL, in valid order and with an explicit future-clock tolerance; merely parseable expiry text is insufficient. Published and ambiguous receipts remain protected. No code has been changed for retention.
