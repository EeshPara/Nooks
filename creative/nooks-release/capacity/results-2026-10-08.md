# Bounded hosted capacity result — October 8, 2026

**Pass for this bounded experiment: 100 distinct authenticated users, 100 WebSockets and 300 private channels. This does not establish 1,000-user capacity or public production readiness.**

Evidence: `report-2026-10-08T07-06-25.470Z.json`, produced by `verify-capacity.mjs`. All services use the existing Nooks Supabase project `lcfcjglybfeozyrjjikk`. HTTP runs through the actual browser API handler in a local loopback process; its calls use real hosted Auth/database, and WebSockets use real hosted Realtime. Email confirmation was deliberately performed by the admin fixture API, with no email sends. No quotas, purchases or production source were changed.

The workload schedules approximately eight API requests per second when active. **Scheduling pauses during the 11.034-second sequential reconnect phase**, so this is about 109 seconds of active scheduling inside the 120-second window, averaging 7.22 requests/second overall. It is not an uninterrupted two-minute load plateau. All sockets remained within the 100 bound; reconnects close a user's old channels/connection before reconnecting that same client. API latency excludes waiting for the local start-rate gate. Fanout latency is transport receipt, not visible UI refresh latency.

The generator checked hosted Auth/DB health before fixture creation, ramped conservatively, respected password-grant rate limits with 2.5-second login spacing, and used a global API start-spacing floor of 90 ms. The stop threshold was more than 2% errors or p95 above five seconds after 20 measured requests. These were stop bounds, not a production SLA.

Cleanup disconnects channels, removes only this run's private room/account/Auth fixtures and revokes sessions. Exact remaining private throttle topic IDs are recorded in the report for the root agent's separate guarded SQL cleanup; the shared directory topic must be preserved. That small cleanup step is separate from measured performance and was not performed by this harness.

## What remains unproven

Public Vercel routing/configuration, email onboarding, browser/native UI convergence, real user device performance, long-duration behavior, multi-room workload, cold starts, provider billing/connection headroom, 1,000 concurrent users and operational recovery. This result supports a bounded real-service test claim, not a general scale guarantee.
