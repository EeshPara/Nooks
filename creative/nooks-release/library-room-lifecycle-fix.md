# Shared-library invitation and room lifecycle

October 8, 2026. Scoped source correction for the invitation issue recorded in `library-invitation-owner-audit.md`. No live accounts, invitations or backend fixtures were created by this work.

The former shared-room effect reset ordinary state only after rendering, and reused a `live` boolean across requests. An owner or invitation change could render the old private heading/material state before the reset; a late A response could then overwrite a B room after the next effect set that same boolean true.

`SharedLibraryRoom` now creates its stateful content with an identity including workspace owner, account status, invitation ID and token. Owner changes, loading/expired/signed-out transitions, and accepted invitation changes therefore replace the old content during reconciliation. The previous state is never passed into the new content. Each mounted effect has its own lifetime object; all initial reads and subsequent picker, refresh, save and comment completions check that lifetime before changing data, error or busy state. A stale save rejects its caller rather than claiming success in an obsolete editor.

Deliberate invitation changes first consult an owner-bound imperative guard. Current edit/comment/busy values update synchronously with their setters. When blocked, the invitation controller restores the accepted hash using `replaceState`, preserves the existing history state and pathname/query, keeps edits mounted, and explains how to finish. The user saves/cancels an edit or sends/clears a comment, then opens the other invitation again. No native confirm dialog is used. A handle belonging to a previous identity cannot inspect or block the new identity.

Within a room, pending requests or unsent comments also prevent material selection/edit/new-note/copy actions. StudyView exit cannot hide an unsent comment. Ordinary dialog Close uses its existing blocked/queued-dismiss behavior while an edit, request or unsent comment exists; sending or clearing the comment releases that block. The comment textarea remains visible and editable while unsent. Same-tick duplicate save attempts are rejected before a second tool call.

The 12 focused tests execute extracted actual room effects/actions/render expressions, invitation navigation and keyed wrapper output. They cover late A success/error, effect replay, identity/status/token replacement, signed-out title exclusion, synchronous edit/comment protection and accepted-URL restoration, successful navigation retry, pending/duplicate save, every late-operation success/error/finally, comment selection/picker/dialog/StudyView protection, and failed-save retention. These are source-level handler/render tests, not a mounted React reconciliation implementation.

Its Vite-only transformation replaces this file's account/tool imports with in-memory fixtures and inserts labeled QA controls. It exercises component mounting, hash navigation and owner/status transitions without changing product authentication or making real account/tool calls. Root owns actual CUA verification and will record that evidence separately. This is simulated account/tool behavior, not a live authenticated sharing journey.

Adjacent `ShareLibraryDialog` and `useLibraryShares` were inspected but not independently hardened by this patch. Current callers live under the owner-keyed WorkspaceApp/StudyLibrary, so changing owners unmounts their parent state/callbacks; modal creation and target selection ordinarily close/remount rather than replacing an active target. No additional reachable cross-owner path was established in this audit. Their standalone hypothetical prop changes and same-owner account-status expiry behavior are not claimed fixed here.
