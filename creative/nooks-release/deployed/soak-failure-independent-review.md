## Strong harness-authentication hypothesis

The installed Realtime SDK is version 2.117.2. A Supabase client installs `_getAccessToken` as the Realtime token callback. On a fresh client without an Auth session, that callback falls back to the publishable key. Realtime treats an existing callback as its source of truth even after an explicit `setAuth(user.token)`; callback refresh occurs during connection/join and heartbeat lifecycle. The soak creates precisely such a fresh sessionless socket client and then joins directory, account and room sequentially.

I reproduced the token-state behavior locally with synthetic values and a fetch implementation that throws if invoked: manual `setAuth` initially installs the synthetic user token, manual mode remains false, and a callback refresh replaces it with the synthetic publishable key. An explicit `accessToken: async () => fixtureToken` retains the synthetic user token across that same refresh. No network was contacted and no real credential was used or printed.

This mechanism fits the observed directory-then-account failure, but the missing historical callback telemetry prevents a conclusive attribution of that particular hosted event. The earlier successful harness subscribed its three topics concurrently, which changes join timing; its success does not disprove a sequential callback race. It also does not prove that every old token-refresh behavior was correct.

The production browser uses its authenticated, persisted Supabase session client for community subscriptions, with session refresh enabled. It does not construct the same fresh sessionless client. This finding therefore justifies a harness correction, not a production authentication change or a claim of a product outage.
