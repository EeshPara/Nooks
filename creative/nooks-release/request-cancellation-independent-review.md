# Independent request-cancellation review — October 8, 2026

**PASS for scoped Node HTTP lifecycle hardening. Hosted Vercel cancellation remains unverified and is not accepted as a production capability.** No app source, deployment, platform setting, credential or production data was changed by this reviewer. The current live release and 7.5 quality / 6.5 readiness grades remain unchanged.

## Reviewed change and independent evidence

I inspected `web/server/request-lifetime.mjs`, its integration in `web/server/browser-api.mjs`, the cancellation tests, existing authentication/store transport boundaries and operational logging. The helper attaches request-scoped listeners, distinguishes incomplete request closure from normal input completion, and cancels unfinished response work on actual response closure. Normal consumed IncomingMessage streams can be closed/destroyed while a response remains pending; the implementation correctly avoids treating that alone as a disconnect.

I independently ran the initial ten cancellation tests plus thirteen browser API tests: **23 passed**. After the final hydration regression and signal override refinement, I independently reran the **eleven cancellation tests**, all passing. These are overlapping validation runs, not 34 distinct tests. I also exercised a separate small check that an explicitly null init signal overrides an already-aborted Request signal; it passed. The implementation agent reports thirty combined browser API/operations/cancellation tests; I did not rerun the unchanged operations suite.

The cancellation suite uses actual loopback HTTP for incomplete-upload disconnects during Auth/quota, normal completed request closure, later response disconnect, and successful delayed RPC completion. Its native-fetch upstream sends headers and an unfinished JSON body: downstream disconnect interrupts body consumption and closes that upstream connection. It also verifies existing timeout values, connected-client 503/redacted logging, no response writes after disconnect, listener removal, already-disconnected and abort-ignoring transports, and suppressed artwork-degradation output after a deliberately swallowed hydration abort. All upstream credentials are fixtures; no real provider was called.

No blocking source defect remains within this scope. Retaining the helper in the public handler is safe when the hosting adapter supplies no disconnect events: its controller stays pending, the original timeout remains effective through signal composition, and normal requests retain their existing transport/authentication path. Adapters without event methods are explicitly supported. Normal completed-request closure is covered by real HTTP tests. This is suitable to ship as bounded defensive hardening, with the ordinary postdeploy authenticated canary still required to catch adapter regressions; it does not require enabling platform cancellation. Composed signals preserve caller timeouts and abort reasons, while methods, headers, body and redirect behavior stay unchanged. Cancellation remains attached during native response-body consumption. Subsequent fetches fail before starting after a disconnect, including when intermediate code catches an abort. The handler removes its own listeners in `finally`, does not remove unrelated listeners, and guards both response output and disconnect-induced operational failure reports. Connected-client failures retain their prior handling.

## Writes and limits

Cancellation is a transport instruction, not evidence that a database commit, Storage write or provider generation was rolled back. A remote operation can succeed before the caller learns of cancellation. This patch adds neither rollback nor automatic replay; existing revision/idempotency/recovery rules remain authoritative. There is no new body deadline, database statement cancellation, exactly-once guarantee, refunded generation or measured compute saving.

The code observes Node request/response lifecycle events. It does not implement a Web Request handler or consume a hosting platform's request signal. Thus the local tests establish behavior **if the adapter propagates those Node events**; they cannot establish the propagation itself.

## Vercel contract investigation and recommendation

The official [Build Output primitives reference](https://vercel.com/docs/build-output-api/primitives) documents the current `launcherType: 'Nodejs'` prebuilt interface, but its listed function configuration does not describe cancellation. Current official Vercel source does contain a boolean `supportsCancellation` on Lambda, and the serialized `.vc-config.json` types derive from those Lambda properties. This is evidence of a real metadata field, rather than a guessed field; it does not demonstrate graceful Node event delivery in this deployed adapter. See [Lambda source](https://github.com/vercel/vercel/blob/main/packages/build-utils/src/lambda.ts) and [serialized configuration types](https://github.com/vercel/vercel/blob/main/packages/build-utils/src/deserialize/serialized-types.ts).

The current [Functions API cancellation reference](https://vercel.com/docs/functions/functions-api-reference#cancel-requests) describes opt-in cancellation via `supportsCancellation`, notification on a Web `Request.signal`, and possible termination of the execution context. Work requiring completion needs the platform's supported background-work mechanism. It does not establish that our default Node-style `(request, response)` handler receives a graceful `close`/`aborted` event before termination.

The current single prebuilt function contains authenticated reads, writes, artwork and generation routes. Enabling termination for that entire function changes more than fetch signal composition. **Recommendation: accept this local hardening, defer the hosted opt-in and production cancellation claim.** Before enabling it, use an isolated supported adapter probe to prove actual hosted signaling and define which in-flight mutations must finish or be recoverable. Do not broadly refactor the runtime or assume a boolean alone supplies the missing proof. Existing timeout bounds continue to apply while this gate remains open.
