# Private artwork lifecycle

The generation lifecycle supports explicit operator cleanup without racing normal artwork saves or appearance shares. It does not schedule cleanup or establish hosted Storage evidence. New uploads use immutable `<account>/<sha256>/<generation-uuid>` paths. Existing `<account>/<sha256>` paths remain readable and are never cleanup candidates.

Deploy all reviewed migrations in order before the matching adapter. The generation migration preserves the existing four-argument workspace commit RPC, service-only execution, owner checks, and room-before-focus locking. It replaces that function in place; there is no older callable commit path that bypasses the asset checks. Legacy writes remain accepted, although those objects stay outside generation cleanup and quotas. Once a generation reference has been saved, a rollback build must retain the dual-format reference parser: the older two-component-only parser cannot reopen that workspace. Preserve the fence migration and catalog/tombstones during any rollback.

The adapter reserves a generation before uploading, uploads without upsert, and confirms only a successful upload. An unknown response never authorizes a reference. Hydrated source references are preserved so unchanged artwork does not allocate another generation on ordinary note saves. Request and pin tokens stay in the service; saved appearance references contain only path and MIME type.

| RPC | Contract |
| --- | --- |
| `nooks_artwork_reserve(account, hash, mime, requestId)` | Allocates a generation and a 15-minute pin. An identical live request returns its original generation without extending the pin or consuming quota. Different bytes/MIME with the same request fail. An expired/fenced request cannot reopen. |
| `nooks_artwork_complete(account, path, pinToken)` | Confirms a known successful upload as `ready`. A foreign, expired or fenced pin returns `accepted:false`. It never revives a deleted generation. |
| `nooks_workspace_commit(account, revision, workspace, shareOperations)` | Accepts only owned legacy references or owned catalog generations in `ready` state with matching MIME. The same check covers current appearance, creator drafts and share publication snapshots. Updates reference-retention timing atomically with the workspace and shares. |
| `nooks_artwork_cleanup_claim(account, dryRun, limit, minAgeSeconds, leaseSeconds)` | Defaults to dry-run. Under the common owner lock, checks current/draft/share references, pin expiry and retention before issuing exact-path deletion claims. Malformed or foreign persisted references quarantine affected owner scopes. |
| `nooks_artwork_cleanup_ack(account, path, claimToken, success)` | Acknowledges only a matching live claim; identical completed acknowledgments are retry-safe. Success also requires the exact Storage metadata row to be absent. Neither failure nor success can make a generation attachable again. |

All RPCs and helper functions require the service role. The catalog has RLS and no client grants; the service role cannot delete catalog rows. Its owner foreign key prevents accidental account deletion from silently discarding tombstones. Account deletion needs a separate deliberate lifecycle procedure.

Reservations, completion, cleanup and workspace commits share an account-scoped transaction lock. The lock precedes the workspace row lock and existing room/focus locks. Reference changes either finish before cleanup rechecks them, or see a permanent cleanup fence and fail before saving. Locks are released before any Storage HTTP request. Ordinary saves scan only that account's references and skip catalog maintenance when it has no pending/ready generations. The global malformed/foreign-reference check runs only during explicit cleanup.

The initial upload policy allows 100 new reservations per rolling 24 hours and 128 pending or retained generation slots per account. Reserved, ready and deleting generations count; confirmed deleted tombstones do not. Retries with the same live request do not consume another slot. Quota is checked atomically before an upload reservation is returned. Each new object remains subject to the bucket's 1 MiB maximum. These limits bound accounted non-deleted generations; they do not claim a physical bucket limit because legacy files and late uploads to tombstoned paths can exist. Removing a draft does not instantly free a slot: retention and successful cleanup must finish.

For initial collection, a generation must have no current/draft/share reference, no live upload pin, and at least 30 days continuously unreferenced by default. Operators may choose 1–365 days explicitly. A commit resets the unreferenced timer when the last live reference disappears. A share-only reference protects its file even when the active appearance or original draft changes. Claims are limited to 1–50 paths, default 25, with 15–300-second leases, default 60 seconds.

An initial claim permanently changes a generation to `deleting`. A failed or unknown Storage deletion keeps that fence and schedules a bounded retry. A successful acknowledgment changes it to `deleted`; the tombstone remains indefinitely. After 24 hours a deleted generation can be claimed again for an exact-path re-sweep. This is intentional: a timed-out old upload may arrive after an earlier confirmed delete. A fresh upload of identical bytes gets a different generation path, so a late deletion or retry cannot remove the new file. Never purge tombstones, reuse generation addresses, or bulk-delete an owner prefix.

Run the [read-only inventory](artwork-inventory.md) first in the trusted operator environment. It reports metadata only and cannot authorize deletion. For actual lifecycle candidates, use the service-side `createArtworkCleanup` client with one verified account ID and the existing Nooks project configuration. Its default `run()` is dry-run and calls no Storage API. Review the returned exact generation paths, quarantine status, age policy and batch size. A separate explicit `run({dryRun:false,...})` is required for mutation; no browser route, model tool, webhook or automatic scheduler exposes this operation.

The client validates the whole claim page before any deletion, sends only exact paths to the fixed private bucket, and checks object absence before success acknowledgment. Auth failures, generic 404 responses, redirects, network timeouts and uncertain responses are retries, never deletion proof. The SQL acknowledgment additionally checks metadata absence. If a batch outlives its lease, unprocessed paths remain fenced and retryable. Choose small batches first and review outcomes; `hasMore` is an observation, not permission for an unbounded loop.

Assign an operator and approved cadence before relying on cleanup in production. Record aggregate pending/deleting/deleted counts, quota refusals, overdue retries, quarantine incidents and successful batch outcomes. Keep account/path output restricted. Do not log image data, study content, credentials, pin/claim tokens or private URLs. Re-sweeps, retained tombstone growth and legacy objects require ongoing observation; this source change does not provide alert routing, an operator, a scheduler or a recovery backup. Supabase requires object deletion through the Storage API, never direct SQL mutation of `storage.objects`. [Official Storage deletion guidance](https://supabase.com/docs/guides/storage/management/delete-objects)

Local verification is recorded in [the deterministic race report](artwork-lifecycle-local-2026-10-04.json). Four actual two-connection races cover workspace/share attachment before and after cleanup fencing. Each race verifies real lock waiting and progress by a different owner. Rollback checks cover reservations, confirmation expiry, lost claim/ack responses, share-only retention, permanent fences, late upload re-sweeps, legacy preservation, quarantine, quotas and client-role denial. The PostgreSQL runner uses private Unix sockets, no inherited credentials, no hosted connections and no real image objects. Adapter Storage behavior is tested with mocks. Actual hosted image upload/deletion, operational cleanup cadence and SQL-plus-image recovery remain separate evidence gates.
