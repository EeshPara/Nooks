## Storage lifecycle: implemented generation protocol

The [generation lifecycle](artwork-lifecycle.md) replaces the earlier maintenance-window proposal. Migration `20261004201449_artwork_generation_lifecycle.sql` (SHA-256 `99b79095157822b87391c67f3e0ae94119287b66de36f182ca2fe70570269598`) adds immutable generation addresses, 15-minute upload pins, atomic reference validation and permanent cleanup fences. Source review passed; all nine local migrations and four actual two-connection races passed. The migration was applied to the dedicated Nooks project on October 4, followed by a passing SQL-only rollback test. No image HTTP operation or physical deletion was performed by that test.

New uploads are bounded to 100 reservations per rolling day and 128 pending or retained generations per account. Legacy owner/hash objects remain readable and noncollectible. Ordinary saved artwork remains protected by current appearance, draft and share references. The operator client defaults to dry-run and requires an explicit bounded mutation call; it has no public route, MCP tool or scheduler. Its default retention is 30 days, with a minimum selectable age of one day. Full contract, retries, tombstones, quota semantics and rollback constraints are in the runbook.

Remaining acceptance: deploy and verify the matching generation-aware adapter, exercise actual hosted upload/read and privacy boundaries, then exercise age-eligible physical cleanup through an authorized operator path. Choose the operator and cadence and demonstrate SQL-plus-image recovery. A successful metadata inventory or four database races does not close those operational gates. Rollback builds must preserve the dual-format parser and generation fence.

## Event and metadata retention

The current UI uses authenticated polling. Outbox/webhook dispatch is not required for navigation, presence or saving, and must remain disabled unless a consumer is deliberately configured and tested. Workspace invalidations already coalesce only when never claimed. Community/focus events and eventual delivery history can still grow.

Record aggregate row count, bytes, oldest age, event type, attempt/lease status and growth over a defined interval. Do not log private payloads. Decide retention separately for delivered events, abandoned hints, retrying events and inbox idempotency records. Never purge a leased/retrying event or shorten an idempotency horizon as an incidental maintenance change. A future dispatcher needs a cutover/replay policy, bounded retry/dead-letter handling and deduplication; adding it does not replace retention.

Implement any pruning as a bounded, reviewed operation with dry-run counts, a maximum batch, transaction/lock timeouts and regression cases for active leases, late acknowledgments and retries. Current production history remains preserved. Operator-approved retention periods and scheduled execution are still open; this document chooses neither silently.

## Failure and recovery procedure

Before a pilot, assign the person responsible for triage and recovery and record where they receive alerts. Verify an expected, privacy-safe failure on the intended deployment can be traced using its generated request ID, operation, status and timestamp. Confirm logs contain no study content, bearer token, account identifier or raw exception. The health endpoint provides liveness/configuration and recent per-instance observations; `unknown` or a stale observation is not a successful database readiness test. No alert has been sent or destination configured by this checklist.

For an incident: preserve pending writing and request IDs; pause the affected feature or new writes if integrity is at risk; inspect the exact deployed version and redacted logs; distinguish a missing image from unavailable study data; recover using the reviewed procedure; then verify owner isolation, a saved note, a practice retry and a private image before resuming. Never restore over the live database merely to test a backup.

The restore acceptance record must identify backup time, scope, encrypted access, retention, operator, recovery environment, elapsed recovery time and data-loss window. Restore SQL and private object bytes into an approved isolated destination; verify account/login continuity, migrations/ACL/RLS, notes/practice, image hashes/downloads, shares and event replay behavior. Supabase database backups do not include Storage object bytes. See the [local restore report](local-restore-drill-2026-10-04.md) for the precise existing evidence and primary documentation.

For application rollback, select the previous tested commit/build and retain the current database schema unless compatibility has been verified. Do not reverse a migration or restore old data by assumption. A fresh native frame must load the intended bundle; already-open frames may retain an earlier build. Record the final check rather than equating a successful deployment response with a user-visible recovery.
